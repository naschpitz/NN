Handling Class Imbalance

Real-world datasets are rarely balanced. A skin-lesion classifier may see 50× more benign than malignant samples; a defect detector may have 1 defect per 1000 good parts. When one class vastly outnumbers the others, a network can reach high accuracy simply by predicting the majority class every time — while being useless for the minority class you actually care about. This guide explains the two strategies NN-CLI offers, how to evaluate them, and how validation/test losses are weighted.

What "imbalanced" means

A dataset is imbalanced when the per-class sample counts differ significantly. The ratio matters more than the absolute counts: a 2-class set split 50/50 is balanced; split 29 000 vs 440 000 (a ~1:15 ratio) it is heavily imbalanced. The risk is that the loss gradient becomes dominated by the majority class, so the minority class contributes almost nothing to learning unless you intervene.

The two strategies

NN-CLI offers two independent ways to counter imbalance. Pick one — they are alternatives, not complementary.

① Oversample the minority

balanceAugmentation: true in the training config.

During data planning, the minority class is oversampled so the effective training distribution approaches 1:1. The network sees each class equally often. Combine with fullAugmentation so the oversampled copies are augmented (not identical repeats) — otherwise the network memorises them.

② Reweight the loss

autoClassWeights: true (or a manual costFunction.weights array).

The dataset stays at its natural prevalence, but each sample's contribution to the loss is scaled by an inverse-frequency weight: rare classes get a large weight, common classes a small one. autoClassWeights computes these as totalSamples / (numClasses × classCount[c]) (the scikit-learn "balanced" formula).

Don't combine them blindly. If balanceAugmentation already equalises the classes, the augmented outputs become ~1:1, so autoClassWeights computes weights that collapse to ~1.0 — a near no-op. Use one strategy, not both. Oversampling changes what the network sees; reweighting changes how much each sample counts. Either shifts the decision boundary toward the minority class.

How to evaluate an imbalanced model

Accuracy lies on imbalanced data. A 1:15 classifier that always predicts the majority class is 94% "accurate" and 0% useful. The confusion matrix (printed by test mode, and stored per-epoch as valConfusionMatrix in trainMetadata) gives the real picture. For each class it reports TP / FP / FN / TN plus precision, recall, and F1, using a one-vs-rest convention (for class C, "positive" = "is C", "negative" = "anything else").

MetricWhat it tells youWhen to trust it
Macro (unweighted mean of per-class scores)Treats every class equally regardless of prevalence.The headline metric for imbalanced data. Insensitive to the majority class swamping the score.
Weighted (support-weighted mean)Weights each class by how often it actually appears.Deployment-realistic, if your deployment prevalence matches your data's.
Micro (pooled across all samples)Collapses to overall accuracy for single-label classification.Useful as a sanity check; do not use as the imbalance headline.
Per-class recallOf the true class-C samples, how many did you catch?The number that matters for the minority class you care about (e.g. "did we miss any malignant cases?").
Per-class precisionOf the samples you labelled class C, how many really were?The false-alarm rate. Low minority precision = many majority samples mislabelled as the minority.
Read the matrix, not just one number. A model can have great macro-F1 yet still trade many false alarms (low minority precision) for high minority recall. Decide which error costs more — a miss (FN) or a false alarm (FP) — for your application, and tune toward that.

How validation and test weight their loss

A subtle but important point: the reported loss and the reported accuracy are separate things. The confusion matrix (accuracy, precision, recall, F1) is always computed unweighted — argmax doesn't care about weights. But the loss reported during validation and test is class-weighted, computed from each set's own class distribution via the same balanced formula.

  • Validation weights its loss unconditionally (it must use real, non-augmented held-out images, so oversampling isn't an option — weighting is the only way to keep the minority class from being drowned out of a single scalar loss).
  • Test does the same, recomputing weights from the test set's own distribution.

Consequence: validation loss and test loss are directly comparable only when test reuses the validation split. Run test against a different dataset and its weighted loss will differ in value even for an identical model — the method (class-weighted) is the invariant, the number is adaptive per dataset.

Worked intuition: prevalence drives the error mix

On a 1:15 dataset, even a model with a lower false-positive rate than false-negative rate can produce far more false positives in absolute terms, simply because there are 15× more negative samples to misclassify. If your test shows, say, a 6% false-positive rate on the majority class versus a 2% false-negative rate on the minority, the raw counts will favour FP roughly 15:2 — not because the model is biased toward FP, but because prevalence multiplies the rate. The confusion matrix's per-class recall/precision rows make this visible where a single accuracy number hides it.

Summary checklist

  • Choose one imbalance strategy: balanceAugmentation or autoClassWeights — not both.
  • Evaluate with the confusion matrix; use macro as the headline, weighted for deployment realism.
  • Decide whether a miss or a false alarm costs more, and read per-class recall vs precision accordingly.
  • Remember validation/test losses are class-weighted and adaptive per dataset; compare values only on the same split.
